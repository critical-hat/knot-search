# knot-search
Programmatic search and data cleanup for band attachments between small knots using grids.

### Recommended workflow
1. Ensure the working directory is set correctly. To ensure no issues arise, and files appear where you expect, set `WORKING_DIRECTORY` to the folder containing these files.
2. Choose a start grid, and confirm whether to use the default from GridPythonModule or its mirror using the second cell in `search.ipynb`.
3. Set `START_KNOT` appropriately.
4. Choose a destination. To keep things clean on longer runs where the data may be split across multiple files, it may be ideal to have a subdirectory just for the raw data. Additionally, provide the name to be used for the file, without the .csv extension.
5. Choose the number of parallel processes to use by setting `NUM_PROCESSES`. This argument is provided directly to the `processes` argument of a Python `multiprocessing.pool.Pool`; if set to `None` it will default to the number of logical cores available on the system. Due to memory and disk I/O constraints, it may be ideal to choose a number slightly less than this.
6. Choose the number of total scrambles to perform. See the rough guide below for an indication of the correspondence between the number of scrambles and the resulting number of band attachments for different starting knots.
7. Choose the number of scrambles to store in each file. The default of 4000 keeps each file to a maximum of around 25 MB for larger (7 crossings) start knots.
8. Choose the scrambling and simplifying effort. It is **strongly** recommended not to set these to `high` or `very_high` without performing small tests first; the time they will take is *much* longer than `medium`.
9. Run the search! There should be no need to modify the code in this cell below these parameters.
10. With data collected, the third code cell (the one marked "Unidentified ratio of a directory") in `data-cleaning.ipynb` can be used to examine the number and proportion of knots in each file within a directory which are unidentified.
11. If desired, one can now use the "Reidentifying" cell in `data-cleaning.ipynb` to attempt to identify some of these grids which were missed the first time.

#### Cleaning up the data
1. Choose a source directory. This should be a directory containing only csv files of the format generated by `search.ipynb`.
2. Choose a destination directory. This is a directory where the output files will be written to. It will be created if it does not already exist. The output files will have identical names to their corresponding input files.
3. Choose a number of parallel processes to use, as above.
4. Set `UNIQUENESS_THRESHOLD`. Changing this to any value above 13 will cause an error, as it can cause incorrect identification of knots. It may, however, be set lower than 13 in order to force reidentification of grids with, say 11 crossings. As an example, a grid may be identified by Sage as either an 11-crossing or a 7-crossing prime knot. If the simplified grid has 11 or 12 crossings, then by default the code will never reidentify it. If `UNIQUENESS_THRESHOLD` is set to 10, however, that grid will be continually rescrambled until either the program ends or the grid is simplified to have 10 or less crossings. If it is set lower, all the files processed as such should be run a final time with it set back to 13 to ensure that no identifications are accidentally missed.
5. Choose the cutoffs for the cleaning process. `NUM_ITERATIONS` is the maximum number of times each individual file will be reanalysed. However, the process may exit a file early if the proportion of unidentified knots to the total number of rows in the file falls below `IDENTIFICATION_THRESHOLD`. For smaller starting knots (3-5 crossings) a final cleaned ratio of approximately 0.5% is reasonably possible (indeed, for 3_1 it is generally possible to identify all but a small handful of grids) as the start knots get larger it becomes more difficult to reach such a low threshold.
6. Choose the scrambling and simplifying efforts, as above.
7. Run the cleaning. A summary of the final numbers of unidentified knots will be printed upon finishing. If desired, it is as easy as copying the files from the output directory to the input directory to rerun the process.

### Approximate runtimes and band attachment counts
The table below shows approximate run durations and numbers of band attachments found using `medium` scramble and simplify efforts, and 2000 scrambles for each start knot.

These runs were performed on a mini-pc with an Intel i5-10500T using 10 parallel processes.

| Start Knot | Run Length | Band Attachment Count |
|------------|------------|-----------------------|
| 3_1        | 13 min     | 43,200                |
| 4_1        | 16 min     | 46,900                |
| 5_1, 5_2   | 20-25 min  | 50,000                |
| 6_1 etc.   | 25-35 min  | 53,200                |
| 7_1 etc.   | 30-45 min  | 56,000-58,000         |
| 3_1#3_1    | 2.5 h      | 57,000                |
| 3_1#4_1    | 5 h        | 60,700                |
